## Goal

Run an authenticated, Docker-hosted service that indexes an approved read-only vault checkout into Redis 8 and returns cited lexical/semantic retrieval while preserving filesystem fallback and atomic index generation cutover.

## Non-goals

- Canonical writes through HTTP.
- Redis as backup or authority.
- Automatic long-term memory extraction.
- Kubernetes or high availability.
- Deep graph traversal or arbitrary attachment execution.

## Requirements

1. Mount one or more explicitly configured vault checkouts read-only and resolve authorization to vaults from server-side identity.
2. Reject content indexing unless the checkout commit is valid and the complete vault passes canonical validation. Bounded control-only admission may precede full validation under ADR-0011; it must not write concept/chunk content or invent validation results.
3. Project concepts and heading-aware chunks with all provenance fields defined in retrieval architecture.
4. Implement provider-neutral document/query embeddings with Voyage AI, OpenAI-compatible, and Ollama adapters selectable at deployment.
5. Isolate every embedding generation and reject dimension/model mismatch.
6. Build a namespaced generation, verify it, evaluate it, and atomically activate it without serving partial state.
7. Run lexical and vector retrieval independently and fuse rankings deterministically.
8. Apply project, type, lifecycle, workflow, sensitivity, trust, and freshness filtering.
9. Return bounded citations, score components, active generation, source commit, and degradation state.
10. Keep Redis private; expose static unauthenticated health/readiness plus authenticated index, search, context, rebuild-status, cancellation, and compare-and-set activation APIs.
11. Authenticate random opaque bearer tokens against constant-time checked digests and authorize every operation through a server-side per-vault scope before Git or Redis lookup.
12. Avoid query/result text, canonical UIDs/paths, credentials, raw dependency errors, and excluded counts/content in logs and metrics.
13. Provide Docker Compose deployment for one host with digest-pinned images, loopback-only service publication by default, health checks, hardened containers, a private Redis network, no Redis host port, and a persistent sensitive-but-disposable Redis volume.
14. Enforce the protocol, approved-commit rule, Redis projection/cutover plan, limits, cancellation, logging, and threat controls in ADR-0010, with ADR-0011's accepted admission, identity, private manifest lifecycle, and initial capacity refinements.

## Version 1 HTTP contract

[`schemas/service/v1/protocol.schema.json`](../../schemas/service/v1/protocol.schema.json) is the normative strict request/response schema. Every JSON object carries `schema_version: "1"`; unknown properties, unsupported media types, compressed bodies, and over-limit values fail before handler work. Context serialization additionally enforces the request budget and a 64 KiB aggregate UTF-8 content ceiling across all items. Responses include `Cache-Control: no-store`. Errors are bounded static objects and never echo rejected values or dependency diagnostics.

```text
GET    /health/live                     public; static process liveness
GET    /health/ready                    public; static dependency readiness
GET    /v1/index                        index:read; all and only granted vaults
POST   /v1/search                       search; one granted vault
POST   /v1/context                      context; one granted active build
POST   /v1/admin/rebuild                rebuild:create; idempotent exact-commit build
GET    /v1/admin/rebuild/:id            rebuild:read; vault-scoped job status
DELETE /v1/admin/rebuild/:id            rebuild:cancel; asynchronous cancellation
POST   /v1/admin/activate               build:activate; compare-and-set cutover/rollback
```

`Authorization: Bearer <opaque-token>` is the only credential transport. Admin credentials are separate from reader credentials. `GET /v1/index` requires no caller-supplied vault and lists only granted handles. Every body-selected vault, path parameter, job, build, context reference, and Redis key is resolved inside a server-side vault grant before lookup. Unauthorized and nonexistent objects are indistinguishable.

A rebuild request names a full Git object ID. Before durable control-only admission, the service checks the configured approved-ref and rollback-window rule, read-only source boundary, exact manifest and expected canonical vault UID, then derives a definitive input-based build ID under ADR-0011. Complete canonical validation and policy checks run in the separately owned asynchronous builder before output attachment or any content projection write. Rebuild does not activate implicitly. Only a complete evaluated build may be activated, and activation names the expected current build so races fail observably.

## Service configuration contract

Deployment configuration is non-canonical and fail-closed. Each configured vault supplies a public handle, expected canonical vault UID, read-only checkout, local approved ref, rollback window, opaque Redis namespace seed, and provider-approved sensitivity classes. Secret files supply token verifiers, Redis ACL credentials, telemetry HMAC material, and provider credentials. Startup rejects more than 64 vault grants per token, duplicate handles or UIDs, writable/mismatched checkouts, missing approved refs, plaintext token entries, undeclared provider classes, absent limits, or Redis namespaces shared by different vaults.

The authorization matrix, token lifecycle, exact-commit approval, Redis key/index plan, build state machine, activation transaction, Compose threat model, deadlines, concurrency/rate limits, and safe logging fields are normative in [ADR-0010](../architecture/decisions/0010-service-protocol-auth-and-projection.md), as refined for admission, identity, and capacity by [ADR-0011](../architecture/decisions/0011-bounded-rebuild-admission.md).

## Acceptance criteria

- Redis can be deleted and rebuilt from an exact Git commit with equivalent indexed projections.
- Search returns source UID/path, exact commit, heading, bounded excerpt, trust, freshness, and score explanation.
- Cross-vault attempts fail for an ungranted request-body vault, foreign job/build IDs, and mixed-vault context references; authorization never depends on Redis filters.
- Embedding failure returns lexical results with explicit degradation; Redis failure produces an unavailable response that causes the extension's local fallback.
- Partial or failed builds never replace the active complete generation; missing/corrupt active pointers return unavailable rather than empty success.
- Duplicate rebuilds converge on one controller job/build identity, a vault has at most one non-terminal rebuild, and terminal retries fence stale workers; cancellation cannot activate or remove the serving build; compare-and-set activation, self-activation, and rollback reject races.
- Expired, revoked, malformed, foreign-vault, and wrong-scope tokens/jobs/builds fail with static non-enumerating errors.
- A model migration can shadow-query, cut over, and roll back without mixed vector ranking.
- Warm service-side retrieval meets p95 under 500 ms on the initial benchmark excluding external embedding latency.
- A record assigned an excluded class produces no Redis projection or chunk, no embedding input, and no search/context result; its UID, path, and marker content are absent from logs and metrics while an included control record remains retrievable.
- Docker exposes no Redis host port in the default configuration.
- Restart, cancellation, duplicate rebuild, malformed concept, oversized input, and provider-rate-limit paths are tested.
- Golden input recipes distinguish vault scope/artifact/policy changes and remain stable across equivalent clone relocation and approval-tip/epoch changes; output hashes remain mandatory verification evidence.
- Absent-output claims, explicit fenced `beginBuilding`, one-time validated attachment, and cancellation/cleanup in both phases reject stale owners, placeholder counts, mismatched descriptors, and premature content writes.
- Admission satisfies the ten-second budget at initial scale with one service-wide preflight and one builder, no unbounded queue, and retrieval p95 below 500 ms during work; source checks are not weakened to pass the budget.
- Disconnect and uncertain Redis outcomes never falsely report no job, lose accepted work through socket cancellation, launch twice, or release quarantined capacity without confirmed teardown/ownership recovery.

## BK-017 projection slice

**Implementation snapshot — migration pending:** this local non-serving API still uses the earlier output-derived ID. ADR-0011 supersedes that identity requirement for controller integration; the snapshot below documents existing behavior, not permission to wire the legacy recipe into the accepted controller.

`prepareLexicalProjection(root, { sourceRef, config, signal? })` is an internal, non-serving preparation API. `sourceRef` must be a full lowercase Git object ID. Deployment-owned `config` supplies the expected `vaultUid`, explicit `approvedSensitivityClasses` (at most 64 unique profile-valid tokens), `maxChunkBytes` (16–65,536), and `maxChunks` (1–250,000). Unknown configuration fields fail. Core completely validates the exact commit and applies exclusions and mandatory secret detection before projection; the service checks the commit-derived vault UID and class declarations/approval. Parsed heading/link strings receive the same policy checks, including entity-decoded and formatting-joined identities. There is no public unchecked record-to-projection function.

The current local build identity hashes canonical vault UID, exact commit, profile, exact manifest hash, normalized deployment class/secret policy, projection/parser/chunker/preprocessing versions, chunk byte size, canonical JSONL output hash, and an explicit null embedding generation. Approved class order does not affect identity. A valid empty included corpus retains its commit and yields zero concepts/chunks. Excluded identities/content/counts are absent from returned projections and static failure results.

Projection preserves tags, typed relations, outgoing Markdown destinations, both OKF verification forms, verifier identities, lifecycle/workflow, stale date, and exact source citations. Heading-aware chunks preserve top-level ATX/Setext heading paths, keep heading-only sections searchable, ignore fenced pseudo-headings, split only at UTF-8 scalar boundaries, and label content untrusted. Projection parsing runs in an on-demand worker with a bounded heap and six-hour ceiling; abort, worker/dispatch failure, and chunk overflow never return partial projections. Worker shutdown is awaited. This is not an initial-scale performance qualification.

This slice does **not** authorize history, prove a read-only deployment mount, write Redis, create/complete/evaluate a controller job, or activate a generation. Approved-ref/rollback-window enforcement, whole-ingestion isolation/deadlines, Redis fencing/leases/query execution, runtime limits, context/admin routes, evaluation, and hardened Compose remain required before BK-017 delivery. OQ-007 still blocks real non-public indexing without data-owner approval. See [partial evidence](../planning/evidence/BK-017.md).

## BK-017 fenced candidate-storage slice

**Legacy implementation snapshot — preserved:** the existing count-bearing `claim()` requires a fully prepared projection and retains its original IDs/layout. The separate S6 input-identified operations below now implement ADR-0011's version-2 absent-output manifest, fenced `beginBuilding` and immutable attachment. No legacy ID/layout is aliased, relabelled or dual-written; zero-count placeholders are not a migration strategy. The S7 component below supplies owned reconciliation; completion and serving remain S8 work.

`RedisCandidateStore` is a trusted, non-serving builder primitive, not an HTTP authorization boundary. It receives a configured vault UID, a 32–64-byte deployment HMAC key, and an injected Redis command executor. Namespace identity is immutable at runtime; all keys derive from one validated `bk:v1:v:<HMAC>:` prefix inside Lua. Commands contain no canonical vault UID. The executor must not log payloads and must honor its supplied cancellation signal. Calls have a two-second maximum wait (configuration may lower it); a deadline/disconnect after dispatch leaves an **unknown mutation outcome**, never proof of no write. There is no automatic command retry.

An explicit per-vault `startProcess()` increments the owner epoch and atomically marks that vault's sole prior non-terminal controller `failed`/`INTERRUPTED`. A bounded `control` hash stores epoch, monotonic fence counter, and the current job ID; this avoids an unbounded startup job scan. Each claim creates a queued job/build manifest and a 30-second renewable fenced lease, or returns the same live controller for a duplicate build. A different non-terminal build conflicts. The controller must start a worker only when `created` is true. Expired leases cannot be renewed or resurrected; this slice recovers abandoned work through a fresh `startProcess()`, not automatic resumption. Epoch/fence counters fail closed on exhaustion without invalidating the last valid lease.

Every candidate batch, renewal, and worker terminal transition checks the current owner epoch, controller, build, fence, and live Redis lease in the same Lua operation. Batches are contiguous and no-replace: 1–128 records, at most 1 MiB encoded JSON, within 50,000 concepts / 250,000 chunks. Callers supply only the previously validated/policy-filtered projection; this low-level store does not reapprove Git or arbitrary raw records. RedisJSON multi-set preserves exact JSON shapes, including empty arrays. Expected type/offset/JSON failures are preflighted before payload writes. Lua errors do not roll back earlier commands: unexpected dependency faults may leave a partial **non-serving** candidate and require failure/recovery plus cleanup, never activation.

Cancellation first marks both controller and candidate `cancelling`, which fences further payloads, then the current worker acknowledges `cancelled`. Failure/cancellation never relabel a serving build. Terminal retries wait for explicit bounded cleanup (at most 128 ordinal keys per call); cleanup reserves/scans the full declared ordinal range, including possibly-written keys after an uncertain failure, and removes the old manifest before a new controller may claim that build. It preserves active, previous, complete, live-reader-leased, and non-terminal data. Terminal job status remains addressable after candidate cleanup; retention/GC of job metadata is a later controller gate.

This adds no complete/evaluated transition, activation, reader-lease acquisition, Redis Search index, production connection/configuration adapter, or new HTTP route. Service startup must initialize its configured vault stores before exposing work, and the full approved-ref/auth/policy, whole-ingestion isolation, evaluation, reader/activation, and hardened-deployment gates still apply. `npm run test:redis --workspace @bookie/service` runs explicit real-Redis tests against a digest-pinned disposable Redis 8.2.1 container with no network or published port; it is separate from Dockerless `npm run check`. The test image is not a production image qualification.

## BK-017 v2 fenced output attachment (S6)

The private store reuses the existing HMAC namespace and bounded executor; Redis is not source/client authorization. `startProcess()` advances the owner and interrupts every prior nonterminal claim, including queued attempts without launch evidence. `setConfigurationEpoch(epoch)` publishes a current-owner, monotonic positive safe integer through `9007199254740991`; canonical decimal strings on the Redis wire avoid Lua/cjson precision loss. The S7 component below owns the configuration-publication interlock.

Allocate and retain `createCandidateJobId()` before `claimInput(trustedRecipe, attemptId)`. The v2 job/manifest bind the source, recipe/manifest/policy digests, owner/fence and configuration epoch; raw recipe serialization, canonical UID/path, content, excluded inventory and expected final counts are not sent/stored. The `outputDescriptor` field is absent, not null/empty/fabricated zero output. Zero append/cleanup cursors count actual work. Legacy and v2 duplicate recognition stay distinct; a retained attempt ID is not a retry permission.

`beginBuilding(inputLease)` explicitly transitions queued to building under the same current owner/controller/build/fence/live lease/configuration epoch. Exact replay is a no-op only while building. Worker launch remains controller-owned and must follow confirmed transition; no v2 payload write is allowed yet.

After actual complete S5 verification, `attachOutput(inputLease, encodedDescriptor)` performs one whole-descriptor HSET. Both Node and Redis validate the existing exact encoding and recipe binding; attachment requires building, the same live owner/configuration/fence and protected-data checks. Identical replay is allowed only under that same still-live building ownership. Conflicting output leaves the first descriptor immutable; the controller must fail the non-serving attempt with static INTERNAL. Parsing an encoding is not proof of source authorization.

`readCandidate(jobId)` validates either phase and returns frozen private metadata with no fabricated counts; an optional encoded descriptor identifies the attached phase. Malformed present fields, versions, counters or phase/state combinations fail closed. Null means an absent manifest after terminal cleanup, never empty output or a missing complete generation. `readJob()` preserves the existing five-field public shape and retained terminal status.

Renew/cancel/fail/interruption work in both well-formed phases under ownership/state rules. Before-output terminal cleanup requires zero cursors and removes only owned candidate metadata/matching current-job linkage; it preserves job status and never guesses payload keys. Attached cleanup scans the full declared ranges, at most 128 keys per call, including uncertain unacknowledged writes. Active/previous/complete/reader-leased/nonterminal data stays protected. Admission validates the current complete manifest and rejects manifestless retained payloads instead of assigning them to replacement cleanup. Canonical numeric zero is exactly `0`, never a literal `-0`, in both Node and Lua validation. Genuine empty output is admitted only by a complete validated descriptor.

Dispatched mutation timeouts/cancellation, dependency faults and unusable acknowledgements expose static failure plus `outcome: "unknown"`; cancellation remains AbortError. Retain attempt identity and reconcile boundedly; no automatic mutation replay, duplicate launch, false no-job or uncertain capacity release. Redis fencing does not establish process teardown. The S6 slice itself adds no controller or HTTP operation; S7 below now composes it. No index, stored-stream verification, evaluation, completion or activation is added by either slice; these remain S8 gates.

## BK-017 owned rebuild controller (S7)

`createOwnedRebuildController({ runtimeIdentityFile, configuration, stores, confirmPreviousWorkersStopped })` composes the genuine S5 builder and configured S6 stores outside admission. Configuration is a frozen `{ epoch, sources, tokens }` snapshot; store namespaces are unique and bound to the source vault UIDs. Runtime identity stays deployment-owned and externally provisioned. Requests cannot supply a recipe, runtime proof, raw records or supervision assertion. The lower-level `OwnedRebuildController` is an explicit trusted component boundary, not an HTTP injection surface.

Startup fences/initializes every configured vault, interrupts prior queued as well as building claims, never resumes work, and stays closed until the required deployment supervision operation confirms old worker groups stopped. It then drains bounded terminal cleanup with retained status and all S6 protection rules. No production supervisor or default confirmation is supplied. Redis fencing and lease expiry do not prove process death.

Admission authorizes/rate-limits before lookup, owns one service-wide preflight and one builder reservation without a queue, and enforces the accepted ten-second/seven-second-plus-teardown/two-second-remaining budgets. Duplicates reapprove current source/configuration and converge through the original attempt without reserving or releasing another slot. New attempts retain generated identity before possible dispatch and obey reserve → confirmed claim → confirmed fenced building → pre-spawn single-launch flag. The six-hour monotonic ceiling begins conservatively before claim dispatch, not on acknowledgement or parser start. Accepted work has a socket-independent signal and ten-second lease renewals.

Unknown replies reconcile only through up to three bounded original-attempt owner-epoch observations. No blind mutation replay or terminal/phase inference from absence is permitted. A matching current live `cancelling` observation retains the original lease, forbids launch and acknowledges cancellation only after confirmed teardown. If cancellation wins while failure is pending, recovery may advance once to that distinct acknowledgement; neither failure nor an uncertain acknowledgement is replayed. Fixed dispatch history belongs to the attempt's lifetime, including shutdown/late callbacks and uncertain recovery fences, not merely one retirement invocation. Unresolved mutation or teardown outcomes quarantine capacity and disable admission pending supervised recovery; late replies cannot replace a later reservation. Terminal retirement requires confirmed owned-worker teardown and a terminal transition or superseding owner fence, then bounded protected cleanup. `ingestion-error` is not teardown proof. Explicit cancellation works before and after attachment. Shutdown stops admission but does not claim an unconfirmed process group died.

`reload(next)` closes admission under a publication interlock, aborts prior preflight/owned work, waits boundedly on the active claim/worker, fences all namespaces and interrupts old attempts before publishing a strictly increased epoch and current auth/source snapshot. Namespace/UID registry changes require supervised replacement startup. HTTP and S5 preflight use that current snapshot rather than stale independent verifiers. A failed publication disables admission/readiness unconditionally, including when a pre-dispatch claim has already released its captured reservation.

An already-started ready controller may be passed as `rebuilds` to `createBookieService`; only then are the existing v1 rebuild/status/cancel routes registered. Without it they remain absent. Strict request/response schemas, five job fields, eight states and all legacy IDs/layouts are unchanged. Status/cancel have no vault query selector and visit only currently authorized configured namespaces; foreign and nonexistent jobs remain indistinguishable. Errors/logging retain the static no-content contract. Readiness includes controller admission health; service close shuts the controller down.

Complete genuine S5 output attaches once under the live epoch/fence. **Attachment remains `building` and retains the reservation/renewable lease.** S7 adds no payload append, index, stored-stream verification, evaluation, completion, activation or serving. S8 must supply these next stages rather than infer completion or release capacity from parser settlement. Fault/race/process/real-Redis and fresh immutable-image evidence are [recorded separately](../planning/evidence/BK-017.md#s7-owned-controller--2026-10-30-utc); production supervision/startup/acknowledgement guarantees and REQ-031/032 measurements remain S8 gates. BK-017 stays Ready/partial, SPEC-004 In progress, with existing trust/portability/approval assumptions unchanged.

## BK-017 approved-history ingestion slice

The core `resolveApprovedGitCommit(root, { sourceRef, approvedRef, rollbackWindow, signal? })` reuses hardened argument-vector local Git plumbing. `sourceRef` is a full lowercase SHA-1/SHA-256 object ID. Deployment supplies a full local `refs/...` name (not a revision expression or replacement ref) and an integer rollback window of 0–1,024 first-parent edges; zero means tip only. Annotated tags may resolve to commits. The literal ref is read once using `show-ref --verify --hash` (no Git name guessing); annotated-tag peeling uses only that captured immutable object ID. Each visited raw commit, including the requested commit, is bounded to 1 MiB and hash-checked with Git's object header. Only its literal first parent advances the walk. Merge-side parents never confer approval; grafts, replacement refs, or shallow revision-walker state cannot manufacture or hide ancestry. Missing required objects fail closed without fetching. On-disk object stores remain a deployment trust/mount concern; inherited Git object/repository/config selectors are ignored. Approval success returns only `sourceCommit` and `approvedTip`; ordinary rejection/read failure is static `source-not-approved`, malformed configuration throws static `TypeError`, and cancellation rejects `AbortError`. This proves history, not client authorization, a read-only mount, vault validity, or activation permission.

`prepareApprovedLexicalProjection(root, { sourceRef, approvedRef, rollbackWindow, config, timeoutMs, signal? })` snapshots deployment inputs, then runs that history proof and the entire exact-commit export/validation/policy/projection window in a dedicated subprocess. Its required deadline is 1–21,600,000 ms and includes ingestion rather than just chunk parsing. The POSIX subprocess starts a private process group, has a 1 GiB V8 old-generation ceiling, ignores inherited Node loader flags/environment, and discards stdout/stderr. The supported/verified host is Linux; Windows returns static `ingestion-error` without spawning, while portable core/filesystem APIs remain available. Parser workers and non-detached Git children belong to the same killable group. This is resource/cancellation isolation, not an OS authorization sandbox, a complete RSS bound, or an initial-scale qualification.

Successful output is the unchanged validated projection plus `approvedTip` outside immutable build identity. No partial projection is exposed on failure. The outer caller owns the builder signal and may compose explicit cancellation with service shutdown; it must not use submission-disconnect as that signal once work is accepted. Deadline returns static `deadline-exceeded`; cancellation rejects static `AbortError` after process teardown. Startup/IPC/crash/teardown faults return static `ingestion-error`. Normal completion also kills/reaps the ingestion process. If teardown cannot be confirmed within a further one-second allowance, return `ingestion-error`, never success or a claim of completed cleanup; deployment supervision must handle an OS-denied/stuck process. There is no automatic retry.

This internal, non-serving API intentionally does **not** validate read-only mounts, orchestrate durable jobs/leases, write Redis, or expose a rebuild route. A validated mount/configuration boundary and controller admission/concurrency remain required before wiring it to candidate storage; OS permissions must prevent root/.git substitution. Activation must separately re-evaluate current approval and policy. Tests manually round-trip its approved, mixed-sensitivity projection through real RedisJSON; this is not evidence that a controller is integrated. OQ-007 remains open for real non-public data. See [partial evidence](../planning/evidence/BK-017.md).

## BK-017 Linux read-only source deployment slice

`compileSourceDeployments()` accepts 0–64 strict source-deployment records containing exactly `handle`, `root`, `repositoryRoot`, `approvedRef`, `rollbackWindow`, `timeoutMs`, and `projection` (the existing projection configuration, including expected vault UID). Paths are absolute, normalized, bounded Linux paths; each vault root lies beneath its explicit repository root. Handles and vault UIDs are unique, and vault roots cannot overlap; sibling vaults in one repository are supported. Configuration, nested projection settings, and class arrays are copied/frozen. This is the source registry only, not the token, Redis/HMAC, provider-secret, TLS, or complete startup configuration loader.

`prepareDeploymentLexicalProjection(deployment, { sourceRef, signal? })` snapshots one such deployment and runs a mandatory source guard in the existing isolated ingestion process before Git source approval and again before returning a successful projection. No caller-supplied mount assertion or bypass flag is accepted. The lower-level approved-ingestion API retains its separate non-deployment contract. A future controller must resolve an authorized handle to deployment-owned configuration and use the deployment entry point.

The initial supported profile is Linux, an ordinary non-bare self-contained repository with a real `.git` directory, and an immutable service mount namespace administered by the trusted deployment owner. Runtime checks require matching nonzero real/effective/saved/filesystem UIDs, zero inheritable/permitted/effective/bounding/ambient capabilities, `NoNewPrivs: 1`, and a read-only root filesystem. Kernel mount/status files must be on procfs. Mountinfo parsing is bounded to 1 MiB/8,192 entries; malformed/ambiguous records fail closed. Read-only means the actual **per-mount** `ro` flag, not chmod or the backing filesystem's superblock flags. All source and metadata ancestors must be read-only. Writable nested mounts and visible writable bind aliases whose device/root ranges overlap protected trees are rejected. Coverage includes the backing range of every protected descendant mount, even when read-only Git metadata is mounted from a separate device/root.

The guard verifies real non-symlink directory ancestors, rejects a shadow `.git` between the repository and vault roots, and inspects at most 100,000 Git metadata entries at depth at most 64. Symlinks, special files, multiply-linked metadata files, gitfiles/linked worktrees, `commondir`, worktree metadata/config, and on-disk alternates are unsupported. Git config is read through a bounded no-follow handle (64 KiB); Git parses the captured bytes on stdin with includes disabled and inherited Git selectors removed. Only ordinary repository-format/filemode/bare/logallrefupdates/ignorecase/precomposeunicode/symlinks settings, object format, user name/email, remote URL/fetch, and branch remote/merge keys are accepted (at most 256 keys). Includes, `core.worktree`, partial-clone/provider hooks, and other unsupported keys fail without expansion. This deliberately strict profile may require a fresh ordinary clone or removal of unused Git configuration; it does not restrict portable local core/CLI workflows.

Before success, the guard repeats its checks and compares mount-table, directory-identity, and Git-config fingerprints. A changed configuration or mount boundary yields static `deployment-rejected` and no projection. Expected vault UID, approved ref/commit, and sensitivity/secret policy are still checked by exact-commit ingestion. Guard work shares the existing subprocess deadline, cancellation, and teardown contract; no raw kernel/Git/filesystem errors are exposed.

These checks do not defend against a malicious host/root/mount administrator, prove every possible filesystem alias outside the namespace, or replace deployment supervision. Host permissions must prevent untrusted actors from changing protected namespace ancestors. CPU/RSS/PID/network/credential/secret-mount qualification and hardened Compose remain separate gates; passing this source guard is not readiness for serving or proof of an integrated controller. The operator must use a non-root container identity compatible with the checkout's Git ownership policy.

`npm run test:deployment --workspace @bookie/service` builds and tests digest-pinned disposable Node 24.19.0/Git containers. It stages only compiled service/core packages and mounts dependencies read-only; positive fixtures use read-only source mounts, no network/ports, dropped capabilities, no-new-privileges, and bounded CPU/memory/PIDs. Negative cases deliberately relax one constraint or expose a writable alias; a synchronized host-side fixture edit proves the final Git-config recheck. No running application container or real vault is used. This image is a test fixture, not a production qualification.

## BK-017 version-2 input-recipe codec

This encoding prerequisite is separate from runtime-artifact generation/verification and from production admission. `encodeBuildInputRecipe` accepts an explicit data-only input object; it does not authorize source metadata, attest a supplied digest, or assert that supplied version labels describe the running implementation. A disconnected `assembleMeasuredInputRecipe` now rechecks a deployment/source-receipt match, reads implementation version labels shared with the projection worker, and hashes actual staged runtime files instead of accepting a caller-supplied artifact digest. It requires an already-authorized, isolated preflight receipt and a deployment-owned immutable stage: a structurally valid receipt can be forged by its caller, and a mutable/unqualified stage can change after measurement. The helper performs artifact I/O and must not run in ten-second HTTP admission. S5 instead uses `assembleQualifiedInputRecipe` with internally acquired guarded metadata and a non-forgeable live runtime proof; the path-based measurement helper remains disconnected from that trusted path. It neither attests clean-install provenance nor rechecks approved history; the future controller/builder must enforce those gates and compare the claimed recipe. No admission/builder/Redis/HTTP path may use its result until deployment qualification, trusted orchestration, and builder recipe comparison pass. Legacy IDs remain unchanged and cannot be aliased to this encoding.

The exact recipes are compact ECMAScript `JSON.stringify` arrays encoded in UTF-8, with no BOM, trailing newline, locale ordering, or Unicode normalization. Hash tokens are `sha256:` plus lowercase SHA-256 hex. Tuple order is normative:

```text
scope = ["bookie-vault-scope", 1, vaultScope]
policy = ["bookie-index-policy", 1, secretPolicy, secretPolicyVersion,
          sortedApprovedSensitivityClasses, provider]
recipe = ["bookie-build-inputs", 2, vaultUid, objectFormat, sourceCommit,
          scopeHash, profile, manifestHash, policyHash, canonicalExportVersion,
          projectionSchemaVersion, parserVersion, chunkerVersion,
          preprocessingVersion, maxChunkBytes, runtimeArtifactHash,
          embeddingGeneration]
```

`secretPolicy` must explicitly be `reject-detected`; `provider` and `embeddingGeneration` must explicitly be null for this lexical codec. Policy classes are copied from one closed descriptor snapshot of a native array; proxies are rejected before observing executable properties. They are unique, profile-valid ASCII tokens (0–64, length 1–63), sorted without locale dependence. Missing fields/defaults, proxies, accessors, unknown own fields (including named/symbol array extras), malformed hashes, mismatched commit/object format, non-null vector/provider settings, invalid versions, and invalid chunk bounds throw static `TypeError` / `Build recipe inputs are invalid.` Version labels are explicit 1–128-character ASCII alphanumeric/dot/underscore/plus/hyphen tokens, not an attestation or registry of supported implementations. Profile is `1.0`; chunk bytes retain 16–65,536. Scope is an empty root or normalized relative POSIX directory, at most 4,096 UTF-8 bytes / 64 segments / 255 bytes per segment, with no empty/dot/Git-metadata segments, backslashes, controls, or lone surrogates. Unicode scalar sequences remain byte-distinct; spelling changes are not silently normalized.

The [literal golden vectors](../../apps/service/test/fixtures/build-recipe-v2.json) and [increment evidence](../planning/evidence/BK-017-adr0011-recipe-codec-trial.md) record encoding verification; their artifact hashes/version labels are synthetic fixtures.

The frozen result contains `serialized`, `scopeHash`, `policyHash`, `recipeHash`, and `buildId` (`bld_` plus the recipe's hex digest). The serialization includes private canonical UID/manifest identity and must not be logged, put in a control record, or exposed through v1. It contains only a digest of scope. A syntactically valid artifact hash is **not** artifact verification; synthetic digests belong only to tests. A real reproducible artifact digest covering the required runtime/dependencies and pinned Node/runtime profile remains mandatory before use. Output hashes/counts stay mandatory later verification evidence, never input-ID fields.

The codec has no place for clone paths/remotes/inodes, approval tips/ref names/windows, epochs, namespace keys, job/request IDs, timeouts, count ceilings, or canonical/projection output hashes; passing those as extra properties rejects rather than silently discarding them. Golden vectors must pin both object formats, empty and Unicode/escaped scopes, empty/class-reordered policy, exact intermediate hashes and final IDs. Pure codec tests do not establish source approval, clone/deployment integration, runtime artifact coverage, output determinism, or initial-scale performance.

## BK-017 disconnected output-descriptor codec

`encodeOutputDescriptor` and `parseOutputDescriptor` are private pure encoding/validation primitives; they neither compute the actual output hashes nor authorize storage or activation. The compact UTF-8 `JSON.stringify` tuple is `['bookie-build-output', 1, recipeHash, canonicalHash, canonicalBytes, canonicalRecords, conceptCount, conceptStreamHash, chunkCount, chunkStreamHash]` (JSON double quotes on the wire). Every hash uses `sha256:` plus 64 lowercase hex digits. Numeric fields are safe integers in 0–536,870,912 bytes, 0–50,000 canonical records/concepts and 0–250,000 chunks; canonical record count equals concept count. Zero records require zero canonical bytes, the empty-stream SHA-256 and zero chunks; zero concepts/chunks require the empty-stream SHA-256 for their respective streams; every corresponding positive count rejects an empty-stream digest. A nonzero record count requires nonzero canonical bytes. Exact canonical serialization is required on reads; whitespace, malformed, unexpected fields, version mismatch and any non-canonical encoding reject with a static error. The encoded object contains only private `serialized` and `hash`; its digest is SHA-256 of serialized UTF-8. [A literal vector](../../apps/service/test/output-descriptor.test.mjs) pins both bytes and an independently calculated digest.

S6's private v2 attachment now consumes this encoding; it is not controller or serving authority: the local projection worker now returns core's complete **included-only** canonical JSONL receipt (exact-byte SHA-256, byte length and record count) plus independently computed ordered concept/chunk projection-stream hashes after successful preparation. Each stream hashes `JSON.stringify(record)` in worker order followed by exactly one LF byte per record, encoded as UTF-8; zero records hash empty bytes. No BOM, locale sorting or self-referential digest fields enter the stream. These hashes are private evidence, not a source approval or the v2 input-derived ID; the legacy local build ID still uses the canonical output hash until migration. The isolated ingestion process now recomputes both stream hashes over the returned worker projections and rejects mismatches with static `projection-error` before returning success; its check also rejects inconsistent canonical receipt shape/counts but cannot rehash canonical JSONL from the projection alone. The private S5 builder now verifies the claimed recipe and complete canonical receipt against its actual sink witness before returning output; S6 now attaches under live ownership; after fenced writes, later completion verification must still recheck actual Redis-stored streams. The worker evidence alone grants no write/activation permission. The legacy count-bearing candidate claim does not consume this encoding. S6 Redis absent-output claim/attachment and S7 owned controller composition are implemented; complete stored-output verification, serving and production rollout remain S8 gates.
