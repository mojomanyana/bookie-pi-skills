# ADR-0013: Exact local recall and producer references

- Status: Accepted for implementation by the operator's continuing ecosystem authorization, 2026-11-04.
- Scope: BK-031, alongside the verified but unmerged BK-030 candidate. This local dependency exception does not mark either item delivered.

## Decision

Keep profile 1.0 concepts unchanged. Add a versioned `bookie-recall.json` control sidecar at the canonical vault root. It binds the existing vault UID and retains suppression/correction controls and metadata-only producer registrations. Initialization is explicit through trusted host authority and first writes an immutable `.bookie-recall-initialized` marker. A marker with missing state refuses normal initialization/synchronization, including interruption between those writes; recovery restores verified retained state. Deleting both files through arbitrary filesystem access is outside the cooperation boundary. Missing, removed, invalid or unsupported-version state is unavailable, never an empty default. Existing canonical records are not rewritten. Rollback disables optional recall/registration while preserving the sidecar and producer originals; deletion is not rollback.

Control changes require the expected exact sidecar revision and trusted authority rechecked under BK-030's cooperating-vault lock. Suppression applies to stable concept/producer identity, including retry and older bundle reuse. A correction retains its predecessor identity and names an exact same-project replacement; it does not reinterpret schema 1.0 relationships or rewrite historical evidence. Existing Decision and Activity/Evidence supersession rules remain meaningful. This is local controlled suppression, not global erasure or hostile-filesystem isolation.

Prepared context is an extractive runtime artifact, not a new canonical concept. It binds the selected Project revision, exact input hashes, bounded UTF-8 representation, manifest/control revisions and trusted destination/policy binding. Reuse revalidates dependencies and recomputes its digest before returning content. Working-tree mode reports commit:null. Exact committed content reuses the validated canonical exporter and carries the resolved commit without implying acceptance; current scope, manifest, correction and suppression rules still apply. The historical excerpt is explicitly canonical-export body Markdown, while sourceHash identifies the original exact committed file bytes; it is not claimed to be a byte-for-byte raw source excerpt. A selected historical UID must still have a current same-project, non-excluded identity with the same declared sensitivity. Current reclassification, deletion or scope movement refuses historical disclosure until separately designed authority exists. Export preflight scans and validates the committed vault, but the sink retains only selected bounded excerpts.

Core local queries remain independent from model disclosure permission. The Pi adapter supplies actual destination identity and trusted policy, and guards every model-visible output. Bundle binding is not a permission token. Unknown policy and unsupported historical-provider confinement fail closed. Session/provider changes cannot retract already disclosed history. General filesystem tools and privileged extensions are outside this tool-return boundary.

Producer registration retains a typed reference and fixed technical identity, never final text or invented canonical metadata. The producer owns original bytes. The stable registration key includes the trusted producer-store instance and excludes content digests, so altered bytes at the same identity conflict; identical retries reuse one receipt. Registration metadata has a separately selected declared, non-excluded sensitivity class. The same producer identity cannot be registered into a second project in this initial local implementation; it conflicts rather than inheriting another project's disclosure. Key-order changes in a typed record do not prevent reuse. A trusted resolver verifies the exact reference before registration. Missing index state never redispatches producer work. Published producer references can be rediscovered by the producer's bounded owner-scoped enumeration; pending admission is not completion.

## Verification

Use deterministic synthetic fixtures: exact-context reuse and amendment, destination/control mismatch, correction/suppression, deleted/unknown sidecar, stale reimport, same-reference retry and changed-digest conflict, authority revocation while queued, interrupted registration and rollback preserving old profile bytes. Reuse existing exact-commit exporter, filesystem guards and cooperating lock. No service/Redis, provider calls or real-vault disclosure decision is needed for these contracts.

Cooperating readers use bounded optimistic source/policy revalidation; this is not an atomic snapshot against arbitrary external filesystem writers. Suppression and producer controls bind stable project UID, not Project text/hash, so a Project amendment invalidates old bundles without restoring hidden inputs. Root/project source revisions are rechecked before a sidecar write; a crash after publication may require reading current state to recover the outcome. Schema migration is explicit: unknown versions and partial initialization are refused, not overwritten.

Resource bounds are deliberately local: recall scans cap 10,000 entries, 2,000 concepts and 16 MiB of concept bytes; committed export preflight additionally caps resource/output bytes at 32 MiB. A bundle selects at most 16 inputs and 48,000 UTF-8 bytes of selected text, with a separate 256 KiB cap on the entire serialized bundle including scope, selectors, provenance and hashes. Preparation/revalidation still invokes bounded linear filesystem checks (including full selected-vault validation); exact final selected-source checks use bounded direct reads. This is not a scalable service/index or a performance qualification. Privacy suppression/exclusion blocks protected identifier references; ordinary correction may retain predecessor provenance links while refusing predecessor content.

## B1 consumer increment (BK-032, 2026-11-04)

Expose bounded model tools for prepared context and exact retained producer references, reusing the A APIs and current trusted disclosure grant. The active human-selected Project supplies scope; model parameters select inputs, not authority. Compact Pi custom entries retain source identities and preparation requests, never source text. Old grants are not restored. A fresh authorized prepare can rebuild from an active-branch manifest with pinned source hashes; old packet reuse still requires exact current dependencies. Bookie absence leaves producer-owned evidence intact.

The optional `bookie:resolve:v1` in-process seam binds the actual current Pi session/cwd and the same disclosure checks. Successful replies carry an untrusted bounded excerpt, exact references, completeness/truncation and a trusted `assertCurrent` callback for final aggregate checks. Missing/stale/suppressed/denied/incomplete/unavailable states remain distinct only where observed. The optional producer remains the owner of original bytes; no shell, dispatch or arbitrary model-supplied producer locator is accepted.

Reference-metadata sensitivity does not authorize final/partial body disclosure. `/bookie-context producer` explicitly authorizes one registered producer owner/instance under the selected project, declared body class and current destination. Alternatively a trusted in-process caller can provide request-specific exact-manifest/part/destination authority. Model tool arguments cannot do so. No automatic body capture occurs. A context hook replaces old Bookie consumer payloads with reference-only notices after restart or changed authority; it does not claim to erase quotations copied elsewhere in conversation or compaction summaries.

B1 restore/replay clarification: compact persisted bundle manifests contain no source body, and model-visible restoration retains only opaque typed handles. The active-branch lookup and fresh current disclosure still govern reprepare. When several remembered outputs validate successfully, aggregate replay checks them again after asynchronous collection; any permission-generation change or failed check removes the whole Bookie body set. A sole successful output needs only its complete validation because no later successful asynchronous validator follows it; each new context request still validates anew, and a later rejected validator or lifecycle change still removes every Bookie body. This introduces no validity cache. These optimistic checks do not freeze external editors. Legacy same-session read/search observations are historical and scope/control/destination-checked, without repeated per-source full-vault scans. Exact-current requirements use the prepared-context consumer. The retained-producer result explicitly separates observed execution state/work from excerpt completeness and sets no semantic approval.


## Scoped work maps and selected improvement inputs (BK-033, 2026-11-04)

The approved local dependent batch adds a bounded `bookie-work-map/v1` JSON body to an ordinary Document. Project, Document, Task, Decision and Evidence retain their existing canonical types and lifecycle enums. The work map is authored plan data, not a runtime registry or an approval record. It references existing exact concept revisions; one Task UID can participate in several plans. Unknown versions, cycles, duplicate identities and missing prerequisites are refused. No service or new canonical frontmatter field is required.

A trusted interactive selection chooses one exact map and plan for the session. Editing a plan or goal reopens alignment; neither a model-selected plan nor `Task.done` supplies acceptance. Task revision hashes bind the Task, applicable inputs, prerequisite revisions and declared output/resource contracts, excluding receipt attachments and unrelated map entries. Current plan/map/Project identities remain separate snapshot provenance. This permits selective reuse without inferring semantic equivalence from prose edits.

Projection resolves required outputs, judgments, resources and runtime observations through explicitly registered host callbacks. Model-supplied observation or approval fields are rejected. An accepted output requires a current exact output plus an independent judgment bound to that output and task revision. A current source alone is not acceptance. Runtime ownership belongs to Pi Daddy; repository and candidate identity belongs to its producer. Missing producers remain unavailable, not permission to start, retry, steal a claim or declare completion. Every asynchronous observation is rechecked before returning a projection. Bookie supplies no scheduler, lock takeover or external release operation.

Maps contain at most 32 tasks, 8 plans and 64 hard edges. One projection selects at most 12 tasks including prerequisite closure and at most 16 exact canonical inputs, with finite text/output bounds. Larger scopes must be explicitly split; traversal does not expand to a repository or the whole history. Supersession, exclusions, current sensitivity and current trusted destination apply through the existing prepared-context path. Returned suggestions are proposals only; authored dismissal/defer/supersession records remain quiet until their exact trigger changes or the operator explicitly requests them. No recurring model monitor is introduced.

Storage uses existing approved create/amend operations and expected source revisions under the cooperating writer lock. There is no implicit plan selection or automatic work-map write permission. Rollback leaves an ordinary readable Document and all original concepts unchanged. Older hosts may read its text but cannot claim v1 projection support. Existing recall-state initialization and restoration rules remain unchanged.

Selected lessons use existing exact prepared-context references and explicitly authored applicability, exclusions and reconsideration conditions. Harness owns proposal, calibration and comparison; Bookie never changes a skill, grants training consent or promotes a lesson automatically.

### BK-033 operational use and boundaries

The shortest current path is: call `bookie_work` with `action: schema` for bounded public authoring help (its synthetic example passes the actual validator); select the canonical vault, Project, classes and actual model destination with `/bookie-context`; use `bookie_read` to obtain exact canonical Project/plan/Task/Decision references and source hashes; create or amend an ordinary Document through `bookie_write` containing one `bookie-work-map-v1` JSON block; select it with `/bookie-work`; call `bookie_work` for the selected task revisions and current projection. Source hashes come from Bookie, not model-written hash recipes. Principal's `principal_workflow resource` returns its current owner-computed Git reference. Receipt bindings copy the task revision from `bookie_work`. No acceptance, execution authority or ability to read another repository follows from possessing a reference.

Each task declares its exact concept, consumed inputs, hard prerequisites, required output IDs/descriptions and optional `reviewScope` (`task` by default, or `integrated`), resource references and effect scope (`unknown` by default). Task revisions include the selected Project goal revision and declared task/consumed inputs/contracts/resources/effects plus predecessor revisions. Plan membership alone does not claim that every plan paragraph is consumed: a task that depends on plan text must list that plan Document in its inputs. Unrelated plans do not invalidate that task; an amended consumed input or Project goal does. A cancelled, done, proposed, blocked or in-progress canonical Task cannot receive a new admission; the operator must explicitly amend it to `ready`. The selected Project must also be active for a new admission. An owner's already-running observation remains visible without re-admission. Accepted outputs remain separate from lifecycle labels.

Hard `dependsOn` requires the predecessor to be currently completed with applicable acceptance and current resources. A review task consumes its producer's exact available output as a resource/input instead of requiring that producer already accepted. This permits build → independent review → accepted output without a circular prerequisite. Rejected output permits a ready task's corrective attempt; an unreviewed output does not silently authorize a duplicate attempt. Exact task/integrated review scope must match. Changed goal, stale resources, rejected/missing predecessor acceptance and unresolved or unknown external effects prevent inferred completion. Runtime owner absence is explicit; it cannot prove external effects reconciled.

`/bookie-work` also selects each task's allowed actual working roots. Repository roots must be individually confirmed from declared task resources and owner-observed as current. Tasks without repository resources use a separately confirmed current working root. Daddy checks the actual routed canonical child directory before spawn; a different worktree/root requires new explicit selection. This is additional applicability checking, not a replacement for Daddy capabilities, grants or workspace leases.

Output and judgment attachments (`outputRefs`, `judgments`) may be added to the selected Document through its ordinary approved amendment path. The consumer refreshes only those attachments while preserving the exact map identity, Project/goal, plans, selected tasks, contracts, inputs, resources, effects, repository scope and disclosure. Owner callbacks verify each new attachment; authored receipt strings never become acceptance. Other intent edits invalidate the selection and require explicit reselection.

Without Principal or another review owner, attach an exact canonical Decision reference with `owner: bookie`, `kind: human-decision`, the exact task/output/review-scope binding and an included stable, accepted Decision. `/bookie-work accept` shows the exact Decision and output binding and asks the human to confirm their review. The Decision's authored `accepted` state alone is insufficient. This fallback is session-local; changing session, branch or destination requires new confirmation. It grants no write, execution, publication or sharing rights. Bookie-owned output references use `kind: concept` and exact canonical path, UID and source hash, so non-development roles can use ordinary canonical artifacts without Principal.

`/bookie-work reconcile` selects one original external/unknown attempt, a current included canonical receipt and human confirmation of the actual external result. Daddy still requires native execution settlement. Receipt identity binds original owner, initiative/task revision, operation/execution and exact receipt bytes. Its reference is capped at 2048 characters before confirmation. The record is operator-confirmed, not a fabricated provider verification or task acceptance. If no live handle exists, recovery-only ownership preserves the old generation and forbids dispatch; an original historical task revision can be reconciled after a current goal amendment when the canonical initiative/Project and selected Task UID still match, without rolling back intent or relabeling the old attempt; after reconciliation, clean release and fresh acquisition provide new ownership. A revoked or changed receipt returns the attempt to required reconciliation. No timeout, process exit or mere semantic approval proves an external effect succeeded or was undone.

A bounded `bookie-work-selection-v1` custom entry retains only canonical vault/Project/map/plan/task references on the active Pi branch. After reload it supplies a UI map-path hint; current sources and user selection are checked again. It restores neither coordinator ownership, disclosure grants nor human judgments. The projection omits unrelated map tasks and handled suggestions unless explicitly requested. It does not erase already-copied prose or compacted history. These mechanical controls support a later C01 fresh-subject continuation evaluation; they do not establish C01–C03 or proactive guidance/model quality.

Version 1 bounds are 32 KiB canonical map JSON, 32 tasks, eight plans, 64 prerequisite edges and 16 suggestions; one selected projection includes at most 12 tasks and 16 canonical inputs in addition to the bounded map Document and returns at most 48,000 serialized UTF-8 bytes. Owner reference payloads are at most 4 KiB. Source/currentness checks use bounded local filesystem scans, potentially repeated per selected input; this is not a service index or scalable scheduler.

Bookie optionally publishes the current guarded projection through Daddy's existing terminal-only dashboard source channel. The bounded view shows selected task dependencies, output/review status, declared repository labels and external-effect state; an omitted-task count is explicit. Registry publication remains unknown unless separately established—Git identity is not release proof. Sequence/freshness and owner-generation checks remain Daddy-owned; source/authority/lifecycle invalidation closes Bookie's publisher. An absent or failed dashboard cannot grant access or prevent a guarded model read.


C09/C12 follow-up: each work Task may declare one exact owner-issued `effectTarget` (owner/kind/opaque structured reference), bound into its task revision. Declared intent is not delivery evidence. The actual coordinator observes pending only from a known not-started attempt state, and records exact target/outcome/provenance against the original attempt and canonical receipt. Bookie UI may attest applied, not-applied or unknown; it cannot manufacture owner-verified provenance. Unknown does not clear reconciliation, not-applied does not satisfy the goal, and only a current applied outcome plus independent applicable acceptance can complete it. A typed package-release target is rendered as published/not-published, without registry lookup or inference from Git or exit status. No additional scheduler, canonical profile or package publisher is introduced.

For package-release targets, `principal_workflow` action `resource` with `packageRelease` returns the exact owner-issued target from the selected manifest and Git candidate; copy that target unchanged into the Task. This is target identity, not registry verification. Historical reconciliation uses the original target retained on the attempt even after the current package/goal changes; the current target is independently revalidated and does not inherit that old outcome. Dashboard details put outcome and provenance before bounded package/registry labels, with exact full target references available in the guarded work projection.

Measured composition performance correction: the optional terminal dashboard publishes the already validated projection as last-observed metadata, with an explicit observation timestamp and a fresh selected canonical-source/disclosure check. It does not initiate another repository, review or runtime owner traversal. Current model output and admission retain their full owner/source validation; no time-based cache or source-currentness grace period is introduced.

Within one read-only work projection, each owner access rechecks the active selection identity, trusted disclosure ticket and fixed human-selected repository roots. Canonical map/input reconstruction remains at the enclosing operation entry/final return and all admission/mutation boundaries, rather than recursively running the whole graph inside each owner authorization callback. This grants no additional root and introduces no cached validity period; a canonical mutation during owner resolution still withholds the final projection.

Nested runtime observations may use the optional trusted `assertObservationAuthority` callback: fresh active selection identity, disclosure destination, Project and recall-control revision, while Daddy retains current owner/lock/generation/native/effect checks. Absent callback keeps the full selection fallback. Only read observations use this path; acquisition, admission, mutation, reconciliation and release retain full selection validation. Pure concept and already-confirmed receipt/judgment observation callbacks likewise revalidate exact referenced source plus fresh authority, with full canonical task/map guards at the enclosing operation and acceptance/reconciliation boundaries. No returned callback grants permission to execute or mutate.

The native same-workspace admission uses `workspaceId: null`; a nonempty routed workspace ID is also valid. In both cases the actual canonical child directory must match that task’s explicitly selected working root. Admission projects only the requested task and its transitive hard-prerequisite closure; full selected canonical intent checks still bracket the operation. Unrelated task owner observations are not repeatedly fetched to admit one task.

A target-only projection may select an implicit prerequisite within the selected plan’s existing transitive closure. It cannot select an unrelated task elsewhere in the map; current UI task selection and full intent guards remain unchanged.

### Applied effects awaiting output evidence

A current owner-backed applied effect with missing or unaccepted required output evidence projects awaiting-acceptance, never ready for another execution. This uses the existing state and remains after current goal, dependency, resource and lifecycle gates; exact output acceptance plus applied effect may still complete. Admission continues to independently reject repeating the applied target.

### Canonical control identity and failed-history recovery (BK-035)

The operator-authorized local repair distinguishes canonical control dependencies from producer registration dependencies. Successful `readRecallState` adds a derived `controlsRevision` over the vault/schema and the full ordered control history, including duplicate effective no-op records, all project identities and supersession references. Every read still validates the complete bounded sidecar and initialization marker. The original exact-byte `revision` remains the mutation concurrency token and producer-registry identity. The durable schema is unchanged. This is not an external anti-rollback journal; unsupported removal/backup replacement retains the existing cooperation boundary.

Canonical context bundles bind the derived control history. Old bundles made with a whole-file control revision become stale and require fresh authorized preparation; they are not migrated or re-signed. A settled metadata-only producer append does not stale unchanged canonical inputs. In-flight preparation retains its whole-state consistency check. Changes to source, policy, controls, selected task intent, resources or disclosure still refuse. Internal read/search/validate, canonical context and work-map tickets opt in explicitly; default and producer tickets retain whole-registry checks and separate producer-body permission. An extension with an older core missing the derived field fails closed for canonical mode.

The context hook still withholds every Bookie body in a request if any remembered validator fails or permission generation changes. It retires only the exact failed remembered entry, so a later genuine current read can recover; a replacement remembered under the same call ID during an await is preserved. Old message bodies remain reference-only. No success cache, permission restoration, automatic scope selection, service or model call is added.

### Bounded canonical selection export (BK-037)

The operator-authorized v7 export increment exposes actual selected canonical JSONL content through Pi, using ADR-0006's exact committed exporter. It preserves complete selected record lines and schema while explicitly labelling the selected-record envelope; whole-vault result metadata and private diagnostics are never forwarded. Explicit paths, current trusted context authority and finite complete-output bounds govern this read-only surface. No model argument opts out of secret detection, selects a disclosure destination or supplies an output file path; ADR-0008's CLI publication deferral remains intact.

Share the committed-context eligibility rules: current selected identity/project/class and correction/control/exclusion state still govern historical bytes, while ordinary current body edits do not erase permitted history. Check private suppressed/excluded identifiers in all decoded record strings, including frontmatter keys/values and relations. Ordinary corrected predecessor provenance is not private suppression: selecting its content remains refused, but a permitted successor may retain its provenance link. Later context delivery revalidates these dependencies and current disclosure; no stored success cache or new permission is added.
