# BK-009 completion evidence

## Scope

Implemented the SPEC-002 Evidence capture transaction and local Git-base validation boundary in `@bookie/core`. Core now copies one explicit local source as exact bytes, publishes a durable content-hashed resource before its schema-valid Evidence descriptor, and compares the proposed filesystem vault with one locally resolved commit to enforce immutable Activity/Evidence history, Decision retention, pinned target identity, resource retention, and current-file tracking.

Filesystem search/inspect, canonical export, CLI commands, Pi tools, secret-detection policy, and any network, commit, or push behavior remain later work.

## Files and behavior

- `packages/core/src/evidence-capture.ts` implements public `captureEvidence()` orchestration, bounded request preparation, schema/manifest/UID validation, coordinated publication, static failures, and observable changed paths.
- `packages/core/src/evidence-capture-filesystem.ts` streams and hashes source bytes, verifies source identity, flushes and rehashes staging files, and rechecks published resource identity.
- `packages/core/src/vault-git-base.ts` resolves bounded local refs/full object IDs, reads exact commit objects through sanitized Git plumbing, checks current index tracking, and applies base-tree immutability policy.
- `packages/core/src/vault-validator.ts` integrates optional `baseRef`/`baseCommit` and classifies only Markdown named by a schema-valid Evidence descriptor as resource bytes.
- Mutation publication now uses atomic no-replace links for absent targets, reports post-publication uncertainty through `changedPaths`, and shares one enforced coordinator contract for concept mutation and Evidence capture.
- `packages/core/test/evidence-capture.test.mjs`, `git-base-validation.test.mjs`, `concept-mutation.test.mjs`, and `vault-validator-review-regressions.test.mjs` cover exact bytes, durability, races, cancellation, tracking, immutability, redaction, object formats, and coordinator violations.
- SPEC-001, SPEC-002, the profile reference, security architecture, data model, toolchain baseline, documentation map, and core README record the delivered contract.

## Public and failure contract

- `captureEvidence(root, request, options?)` accepts an explicit local source path/file URL, absent canonical descriptor/resource paths, complete caller-owned Evidence metadata without `resource` or `bookie.sha256`, and exact body text.
- Core streams without decoding, enforces the manifest attachment limit and an optional lower caller limit, computes lowercase SHA-256, flushes and reopens the stage, and verifies the staged digest before preparing the descriptor.
- Atomic no-replace publication makes the resource durable before descriptor publication and never overwrites a raced target. A descriptor conflict leaves the already durable resource as an explicit orphan; every possibly published path is reported.
- The complete read/validate/stage/publish window is serialized per real vault root and through optional `runExclusive`. A coordinator must invoke exactly once, await completion, and return the same result object; substituted, duplicate, early, or post-completion failures cannot produce false success or an ambiguous in-flight failure.
- `validateVault(root, { baseRef })` accepts a bounded canonical local ref or a full SHA-1/SHA-256 object ID matching the repository format. Full IDs are case-insensitive; abbreviated IDs are rejected even when a same-named branch exists.
- Git execution uses argument vectors and static diagnostics, removes inherited Git repository/index/object selectors, disables hooks, fsmonitor, replacement objects, and lazy fetch, and never uses a shell, fetches, commits, or pushes.
- Current non-excluded consumed files require stable stage-zero ordinary index entries. Excluded paths retain normal exclusion semantics; alternate indexes, intent-to-add entries, gitlinks, tracking races, and untracked canonical files fail closed where applicable.
- Base Activity and Evidence descriptors retain exact path, UID, and bytes; Decisions remain addressable by UID; immutable source targets retain path/UID identity in both trees; base Evidence resources retain exact size and SHA-256.
- Invalid or incomplete Git state returns static `GIT-BASE` with `complete: false`; policy violations remain complete validation failures. Excluded-sensitivity diagnostics disclose neither identifiers nor field-derived paths.

## Red evidence

The first focused tests failed because `captureEvidence` was not exported and `validateVault()` ignored `baseRef`. Test-first implementation and adversarial review probes then observed each of these failures before remediation:

- absent capture targets could be overwritten between final check and publication;
- source/staging tampering, directory synchronization failure, and post-publication errors could be reported with inaccurate changed paths;
- inherited alternate-index/object variables and repository fsmonitor configuration could affect Git behavior;
- nested vaults, gitlinks, intent-to-add entries, late index changes, and SHA-256 object-format boundaries were handled incompletely;
- excluded identities or resource paths could leak from malformed base input;
- Markdown under Evidence roots was either hidden too broadly or classified by malformed/generic Evidence instead of a schema-valid descriptor;
- an abbreviated hexadecimal OID was accepted when a local branch had that name, including uppercase/mixed-case variants;
- valid full uppercase SHA-1/SHA-256 object IDs were rejected;
- tracked nonordinary entries under manifest-excluded paths incorrectly changed exclusion semantics;
- `runExclusive` could substitute the callback result, return before publication completed, or hide a duplicate callback invocation.

Each regression passed after its focused repair. Additional probes covered symlink/hardlink sources and targets, root/ancestor replacement, resource/descriptor target races, staged digest mismatch, cancellation before and during Git reads, bounded/truncated Git output, hooks, replacements, lazy-fetch prevention, immutable edit/deletion/rename, Decision retention, pinned project/relation/support targets, resource deletion/change, and excluded-sensitivity redaction.

## Acceptance demonstrated

- Exact binary source bytes, including NUL and invalid UTF-8, survive capture and match the descriptor's verified SHA-256 and byte count.
- Oversize, changed, deleted, symlinked, hardlinked, or tampered sources/stages fail before publication; safe cleanup leaves no descriptor or resource.
- Resource publication precedes descriptor publication and directory durability; raced absent targets are never overwritten, and a descriptor conflict reports the durable resource orphan.
- Missing or changed Evidence resources and immutable Activity/Evidence edit, deletion, rename, or replacement produce the documented diagnostics.
- Decision deletion, immutable project/relation/support identity replacement, base resource changes, and current tracking ambiguity are detected against exact commit objects.
- Local refs and full SHA-1/SHA-256 IDs work in containing and nested worktrees; revisions, abbreviations, unsafe refs, hooks, alternate indexes, gitlinks, and active tracking changes fail closed.
- Filesystem-only validation remains available without Git and unchanged when `baseRef` is omitted.
- Core invokes no network service, Pi API, `git commit`, `git push`, or process exit.

## Assumptions and follow-ups

- Git-base validation conditionally requires local Git 2.29 or newer; filesystem-only core operation has no Git runtime dependency.
- Node exposes pathname operations rather than portable `openat`/`renameat2`. Participating writers are serialized and observed races fail closed, while OS permissions or sandboxing must prevent a hostile same-user process from repeatedly renaming validated ancestors between syscalls.
- [OQ-005](../open-questions.md#oq-005-default-attachment-size) remains open for the product attachment default; capture obeys the manifest limit and an optional lower caller limit.
- [OQ-009](../open-questions.md#oq-009-pre-write-secret-detection-policy) still blocks CLI/Pi write exposure. BK-009 intentionally remains a policy-neutral low-level primitive rather than inventing detector or override behavior.
- Reviewers observed the existing transitive `fast-uri` audit advisory; BK-009 changed no dependencies and added no URI network sink. Dependency remediation remains separate maintenance work.
- GitHub Actions passed with a warning that `actions/checkout@v4` and `actions/setup-node@v4` target deprecated Node.js 20 and were forced onto Node 24; update those actions separately.
- BK-010 bounded filesystem search and inspect is the next ordered implementation item.

## Drift found and resolved

- The evidence-root Markdown classification boundary was previously implicit. SPEC-001, SPEC-002, the data model, profile reference, validator, mutation scan, and Git-base traversal now agree that only a schema-valid Evidence descriptor classifies a referenced file as resource bytes.
- Exact no-replace publication, directory durability, observable post-publication paths, full object-format handling, and current index rechecks were underspecified before implementation; SPEC-002 now pins those behaviors.
- The pre-existing coordinator prose required exactly-once invocation plus awaiting and returning the callback result unchanged, but the runtime did not detect substituted or early results. Concept mutation and capture now share one enforced internal coordinator boundary.
- Current tracking initially applied mode restrictions to excluded paths. The implementation now matches SPEC-002's non-excluded consumed-entry scope without weakening base-tree rejection of symlinks, submodules, or special modes.
- No accepted ADR or product requirement was weakened or superseded.
