# BK-052: Re-attach memory after a folder moves

The owner decided on 2026-11-17: "Explicit command, you confirm. A Bookie command shows the earlier project it believes this is (matching Git history), with old and new paths, and re-attaches only after you confirm in the terminal. Never automatic and never offered to the model." [ADR-0022](../../architecture/decisions/0022-reattach-moved-project-memory.md) records the design; REQ-035 states the requirement.

## Independent review

An independent review of the first implementation (`8d23cbf`) requested changes. The follow-up commit on the same branch:

- offers a memory only with Git-history or same-folder evidence (the "unverified" offer is removed) and keeps a recorded commit when a later Git probe fails;
- uses a location record only when the binding's key is the hash of the record's own path and folder identity;
- removes, under the store lock, everything an interrupted re-attach can leave, on every run of the command and again before the commit;
- treats a different folder at the recorded path (re-created, re-cloned or restored), or a recorded path that now leads to this folder under another name, as the earlier folder being gone;
- corrects the dialog text (clones and forks match Git evidence, "not found" includes a disconnected drive, unrelated live projects are not called copies, and what Pi Daddy Auto allows after re-attach);
- requires an idle session, compares the automatic seed byte for byte, and passes the folder to Git with `-C`.

## Local verification

Base: `a6c35e7` (pi-bookie 0.7.0, core 0.3.0). Branch: `claude/reattach-moved-project-20261117`. Local checks only, Node 24.22.3; no CI, merge or release has happened.

- `packages/pi-extension/test/reattach.test.mjs` has 28 tests using temporary directories and real Git repositories. A crash is simulated by letting one file operation complete and stopping the re-attach there; each of the 7 file operations without an automatic memory and the 8 with one is covered.
- Against the build of `8d23cbf`, 18 of the 28 tests fail. The 10 that pass cover behaviour that was already correct or guard existing branches that the review's mutations showed untested.
- Full `npm run check`: format and lint passed; repository 464/464, service 323/323, CLI 48/48, core 310/311 and extension 189/190. On `8d23cbf` the same command gives extension 175/176 and otherwise the same totals. The two failures are identical on both and specific to the sandbox: core's chmod-0o500 staging test running as root, and the extension's nested `npm install` failing to complete.
- A single-line mutation check applied 31 mutations to the re-attach logic (the reviewer's 10 surviving mutants, re-applied to the new code, and 21 for the fixes), rebuilding and running `reattach.test.mjs` for each; all 31 were detected.

## Limits

No Pi host, model, provider or JEV run was made; the command was exercised with fake Pi hosts that register real Bookie hooks. A real cross-volume move was simulated by copy and delete, and crashes by stopping at a file operation rather than killing a process. Memories last opened before location records existed cannot be matched (OQ-016), and a folder without Git copied to another volume has no evidence and is not offered.
