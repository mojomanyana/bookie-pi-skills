# BK-015 completion evidence

## Scope

Implemented curated Activity checkpoint preparation, preview, immediate approval, and pre-compaction approval for SPEC-003. ADR-0009 records the structured metadata and sensitivity contract that resolved the checkpoint input ambiguity.

## Files and behavior

- `packages/core/src/checkpoint-preparation.ts` accepts complete caller-supplied Activity metadata and bounded structured sensitivity-labelled fragments; it never consumes a raw transcript or generates canonical identity metadata.
- Core validates manifest classes, rejects secrets and excluded Activity classifications, omits excluded fragments before returning public data, renders all required sections deterministically, and retains a detached canonical request behind an opaque publication value.
- `createCheckpointWithPolicy()` binds publication to the prepared root, target, parent chain, and complete manifest. It reloads the manifest after temporary staging and fails on a changed publication policy.
- Ordinary policy-bearing create/amend rejects Activities, preventing user-facing bypass of structured checkpoint preparation. Policy-neutral low-level APIs remain available for trusted composition.
- `packages/pi-extension/src/index.ts` registers `bookie_checkpoint` with strict TypeBox and `StringEnum` inputs, explicit vault/request paths, cancellable approval, Pi's mutation queue, static operational errors, untrusted-content labelling, and 50 KB/2,000-line bounds.
- Immediate checkpoints require originating explicit approval or TUI confirmation. Pre-compaction checkpoints reserve one session slot before request I/O and retain it through preparation, confirmation, and publication.
- Confirmation identifies only the canonical target and a digest of filtered input; raw vault/request-file paths and excluded fragments are not retained in pending state or displayed.
- Decline, cancellation, no UI, and publication failure write nothing and do not block compaction. `agent_end` and `agent_settled` handlers are absent; shutdown clears staged state idempotently.

## Acceptance demonstrated

- Approved immediate and staged workflows each create exactly one schema-valid Activity through an opaque, policy-bearing, mutation-queued publication path.
- Mixed-sensitivity input retains included context while excluded UIDs, paths, markers, and counts are absent from prepared input, preview, canonical Activity, tool output, diagnostics, and notifications.
- Secret-bearing input fails with a static error and publishes nothing.
- Decline, cancellation, no UI, shutdown, and publication failures create no Activity while pre-compaction handling continues.
- Ordinary agent completion has no checkpoint-writing handler.
- Root, target-parent, complete-manifest, request substitution, queue-wait, and post-staging policy races fail closed.
- Sequential and concurrent staged/immediate workflows cannot occupy more than one session checkpoint slot; over-line confirmations fail before staging.

## Assumptions and follow-ups

- Callers remain responsible for supplying valid Activity path, UID, project, UTC timestamp, actor metadata, and sensitivity labels.
- Sensitivity labels are caller assertions validated for manifest membership; Bookie does not infer sensitivity from prose.
- The accepted SPEC-002 platform boundary remains: portable Node pathname publication relies on OS permissions or sandboxing to prevent a hostile same-principal ancestor rename between syscalls.
- No release-0.1 implementation item is Ready. BK-016 remains blocked on OQ-003 and OQ-004 before service work can begin.

## Drift found and resolved

- Initial prepared output shared nested frontmatter with private publication state. Detached cloning now prevents public mutation from changing approved canonical bytes.
- Initial publication checked sensitivity policy before staging only. Publication now binds the complete manifest and reloads it after staging.
- Initial pending confirmation retained raw vault/request paths. Confirmation now uses only a filtered-input digest and canonical target.
- Initial staging could overwrite or overlap pending work. An explicit session state machine reserves one slot before I/O and through preparation, confirmation, and publication.
- Initial session reservation covered staged workflows but not immediate checkpoints. PR #23 made reservation unconditional and added staged-versus-immediate and parallel-immediate regressions.
- A pre-existing timing-based validator race test became unreliable under repeated full checks; continuous in-place mutation now deterministically exercises the same snapshot-incompleteness behavior.
- No accepted canonical, sensitivity, portability, approval, provider, or degraded-read boundary was weakened.
