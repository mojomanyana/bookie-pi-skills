# BK-014 completion evidence

## Scope

Added explicit Pi create/amend workflows to SPEC-003 through `bookie_write`. Canonical writes use the policy-bearing core APIs and Pi's file-mutation queue; the extension does not commit or push.

Behavioral mutation and concurrency coverage was retained as required by BK-014. No mutation-testing tooling was introduced.

## Files and behavior

- `packages/pi-extension/src/index.ts` registers a strict `bookie_write` TypeBox contract with `StringEnum` action and approval modes plus explicit vault and request-file paths.
- Requests are read from bounded, ordinary, singly linked, no-follow files. Exact bytes are read through a capped positional loop, checked for metadata stability, decoded strictly, parsed once, and hashed before confirmation.
- Interactive confirmation identifies the action, vault, request path, and exact request SHA-256. The same in-memory snapshot executes after approval, so replacement during the dialog cannot substitute content. The dialog propagates cancellation.
- Non-interactive confirmation ambiguity and declined or aborted confirmation fail before publication. An originating `approval: "explicit"` supports non-interactive use.
- Create and amend delegate only to `createConceptWithPolicy()` and `amendConceptWithPolicy()`. Their full read-modify-write callbacks execute through `withFileMutationQueue()`.
- Operational failures throw static bounded errors. Secret failures expose only `WRITE-SECRET`; failures with non-empty `changedPaths` instead require reread and validation before retry.
- `packages/pi-extension/test/extension.test.mjs` covers contracts, TUI approval/decline/cancellation, no-UI ambiguity, request substitution, exact/plus-one request limits, malformed and secret requests, behavioral queue participation, and concurrent stale amendments.

## Acceptance demonstrated

- Explicit create publishes one complete schema-valid concept through policy validation and Pi's mutation queue.
- Explicit amend uses source-hash conflict detection. Two parallel amendments from one source hash produce exactly one success and one `MUTATION-CONFLICT`, with no lost update.
- A behavioral queue test holds the canonical target's Pi queue and proves the write remains pending until release.
- Non-interactive confirmation ambiguity, interactive decline, and cancellation publish nothing.
- Replacing the request file during confirmation does not change the approved snapshot that is executed.
- Malformed, oversized, linked, unstable, and secret-bearing request inputs fail closed without leaking rejected content.
- Source and runtime checks show no unguarded mutation API, network call, automatic commit, or push path.

## Assumptions and follow-ups

- JSON request files keep canonical content out of Pi tool arguments and therefore out of the normal persisted tool-call payload. Callers remain responsible for protecting those local files.
- `approval: "explicit"` means the originating caller already obtained approval; the extension does not infer approval from ambient UI state.
- Pi confirmation is bound to the displayed request hash and executes that exact snapshot, not later bytes at the request path.
- BK-015 is now Ready for curated checkpoint preview and approval behavior.

## Drift found and resolved

- Initial confirmation preceded request loading, allowing request substitution during the dialog. Loading, bounding, hashing, and retaining one snapshot before confirmation closed that race.
- Initial request reading relied on a pre-read size check. A capped positional loop now enforces the memory bound during reads and tests exact and plus-one limits.
- Initial concurrency coverage could pass using only core's queue. The test now behaviorally holds Pi's queue and proves extension participation.
- Initial confirmation did not receive cancellation. The tool signal now dismisses pending confirmation and prevents publication.
- No accepted canonical, sensitivity, provider, portability, or degraded-read boundary was weakened.
